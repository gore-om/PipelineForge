AWS services needed for Sovereign Code
======================================

Recommended production path for tomorrow's test
-----------------------------------------------
Use EKS for this manual test because PipelineForge currently generates Kubernetes manifests. ECS is a valid future target, but ECS would need task definitions and service definitions, which are not the main generated path right now.

Required AWS services
---------------------
1. Amazon ECR
Create two private container repositories:
- sovereign-backend
- sovereign-frontend

These store the backend and frontend Docker images.

2. Amazon EKS
Create one Kubernetes cluster for running the generated Kubernetes deployment, service, secret, and ingress manifests.

Recommended cluster name:
pipelineforge-sovereign-dev

Recommended namespace:
sovereign

3. EKS managed node group or EKS Fargate
Use one of these so pods can actually run.

For easiest manual testing:
Use an EKS managed node group.

4. Amazon RDS for PostgreSQL
Create a managed PostgreSQL database for the backend.

Recommended database name:
ledgerly

Recommended username:
ledgerly_admin

PipelineForge needs the final DATABASE_URL value.

Example format:
postgres://ledgerly_admin:<password>@<rds-endpoint>:5432/ledgerly

Use DB_SSL=true for production-style testing.

5. AWS Secrets Manager or Kubernetes Secret
For tomorrow's PipelineForge test, PipelineForge can generate a Kubernetes Secret manifest with placeholders replaced by your supplied inputs.

For a stronger production setup later, use AWS Secrets Manager with External Secrets Operator or CSI driver.

Required secret values:
- DATABASE_URL
- TOKEN_SECRET
- CORS_ORIGIN

6. AWS Load Balancer Controller
Needed if the generated Kubernetes Ingress should create an AWS Application Load Balancer.

This requires IAM permissions for the controller.

7. Application Load Balancer
The ALB is normally created by the AWS Load Balancer Controller after applying an Ingress manifest.

PipelineForge should produce the ingress host mapping. AWS creates the ALB after the Kubernetes controller sees the ingress.

8. Route 53
Needed if you want a real domain.

Create or use an existing hosted zone, then point the app domain to the ALB DNS name.

Example app domain:
sovereign.yourdomain.com

9. AWS Certificate Manager
Needed for HTTPS.

Create or request a public certificate for the app domain.

Example:
sovereign.yourdomain.com

10. IAM roles and policies
You need IAM access for:
- Azure Pipelines or your local machine to authenticate to AWS.
- Pushing images to ECR.
- Updating EKS deployments.
- EKS nodes to pull images from ECR.
- AWS Load Balancer Controller to manage ALB resources.

11. CloudWatch Logs
EKS and container logs should go to CloudWatch for production observability.

12. VPC, subnets, route tables, and security groups
EKS and RDS need networking.

Recommended layout:
- Public subnets for ALB.
- Private subnets for EKS nodes.
- Private subnets for RDS.
- Security group allowing EKS workloads to connect to RDS on port 5432.
- Security group allowing ALB to receive 80/443.

13. S3 and DynamoDB for Terraform state, later stage
This is not required for tomorrow's manual PipelineForge app test, but it will be needed when we start production Terraform.

Terraform state bucket:
pipelineforge-tfstate-<account-or-env>

DynamoDB lock table:
pipelineforge-terraform-locks


Do we need Jenkins EC2?
======================

Yes, if Jenkins is the selected CI/CD provider and you are not using an existing Jenkins controller.

For the preferred Jenkins flow:
- CI/CD provider: Jenkins
- Cloud provider: AWS
- Jenkins controller or agent with Docker, AWS CLI, kubectl, and Terraform is required

Create or prepare:
- 1 EC2 instance for Jenkins controller
- IAM role or AWS credentials for ECR/EKS access
- Docker installed on Jenkins
- kubectl installed on Jenkins
- aws CLI installed on Jenkins

---------------------------

Expected good result:

Known gaps to watch during tomorrow's test
==========================================

1. Terraform is still starter-level.
PipelineForge may show the right AWS resources but may not yet generate complete production Terraform modules for all of them.

2. ECS is not the primary generated target yet.
If you choose ECS, PipelineForge will need ECS task definition, service, target group, listener, and IAM task role generation in a future stage.

3. Secrets should move beyond plain Kubernetes Secret later.
For production, use AWS Secrets Manager with External Secrets Operator or CSI driver.

4. Runtime dry-runs depend on local tools.
Docker, kubectl, AWS CLI, and cluster credentials must exist locally if you want real executable validation.

5. Full HTTPS requires AWS Load Balancer Controller plus ACM certificate and domain setup.
